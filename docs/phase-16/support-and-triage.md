## What the teacher can report

“Tell your supplied alpha support contact what you expected, what happened and which step stopped you. Include the time, a safe error reference beginning `EG-` if shown, the participant/session code and whether the student paper, answer key or both were affected. Do not send passwords, sign-in links, tokens, student details, raw technical logs or a full screenshot containing private information.”

For document problems, first describe the problem and relevant question number without sending the file. Support checks whether the file contains identifying or licensed material and whether retention permission exists. Only then use the agreed owner-controlled transfer/storage route. Never use a public issue, shared brain, repository or public link for real participant files.

Preserve both originals as a pair. Record file hashes privately before editing. Redact a separate copy if necessary, assign new hashes and label it a derivative; do not present a redacted or Word-corrected copy as the original evidence. Record the application/version, page/section, expected versus actual content, marks/answers/direction and correction effort. Do not ask the teacher to send a full source collection when a small authorized redacted reproduction is sufficient.

## Findings record

Use the header-only [findings template](records/findings.csv) in private storage. Each finding needs: exact build and workflow, safe reproduction steps, observed versus expected behavior, confidence, category/severity, containment, owner, status, repair reference and retest evidence. Link a failed original attempt and its separately identified retest. An unconfirmed hypothesis is not a fixed cause.

Use the canonical categories: release blocker, important usability defect, content defect, or later preference. Record severity separately:

| Severity | Alpha handling |
| --- | --- |
| P0 | Suspected credential/private-data exposure, cross-account access or widespread destructive behavior: stop affected alpha use immediately and notify the owner privately. Preserve minimum safe evidence. |
| P1 | Data loss, wrong answer/key mismatch, invalid paper or a workflow that cannot be completed: stop the affected workflow, record the impact and contain it. Treat semantic correctness defects as blockers even if only one paper is involved. |
| P2 | Material usability or content issue without P0/P1 impact: record evidence and a narrow remedy. Escalate if it changes correctness or prevents completion. |
| P3 | Later preference with no demonstrated blocking impact: retain separately; do not expand the current phase. |

Security/privacy/data-loss/semantic incidents require owner-approved resumption after relevant repair and retest. Do not invent a workaround that suppresses validation, changes source answers silently, shares accounts or exposes reviewer privileges. A manual Word correction remains a finding; it does not prove the product was repaired.
